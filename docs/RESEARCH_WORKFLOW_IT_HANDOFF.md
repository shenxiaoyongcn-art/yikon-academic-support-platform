# 亿康科研项目管理模块｜IT对接与验收交付

版本：2026-09-03 · 业务验证版

## 1. 本期交付与使用入口

平台入口：`/modules/research`，独立业务接口：`/api/research`。

本期把科研模块从通用台账改为可执行流程，并参考用户提供的BMP会议单据链展示方式：

**需求与评估 → 科研立项 → 合同/协议 → 预算占用/付款 → 样本/物料与资源 → 项目执行 → 费用核销 → 验收总结**。

每个环节可点击，显示关联记录数量、当前状态及处理人。合同、付款、资源、费用核销和总结可独立提交申请，审批结果回到同一主项目。费用核销和验收总结在界面业务链中是汇总入口，实际流程先做最终交付验收，再财务核销，不能先关项目后补验收。

- 流程演练：虚拟项目、虚拟医院、虚拟预算；只在当前页面内存中运行，刷新重置。可切换角色，与正式服务使用同一个流程引擎，不是伪造正式审批。
- 正式工作区：认证、组织授权、服务端状态机、D1持久化、追加快照、预算原子锁定和冲突校验。
- 新业务记录与旧BMP导入台账完全分开，不自动覆盖或把旧项目冒充新流程已审批项目。
- 中台审批**不等于**真实付款、实际出库、临床准入或已经同步BMP。

## 3. 三类审批链

### A 客户科研 / 公司投入

需求草稿 → PMO完整性 → 研发评估 → 分析人力 → PMO汇总成本 → 商务核预算包 → 大区批准使用 → 营销预审/审批 → 适用商务/合规会签 → 授权外例外（如适用） → 七项立项承诺 → 启动 → 执行 → 验收 → 核销结题。

预算内常规A类在最后一项批准时，审批快照、预算占用和待对接事件在一个数据库事务中保存。月度、预算内、非重大、非高风险且在营销节点的需求可批量预审；不符合条件的逐条排除并返回原因。批量目前实现“通过”；批量退回为后续扩展，逐项退回已可用。

超预算申请经营销/例外批准后进入“预算额度落实”，商务须有真实增补批准依据并维护预算额度，余额充足后才能锁定和立项。不会因为点击例外同意就允许预算余额变负。营销授权金额未配置时，超预算保守进入授权外例外节点；这是一项上线前须由公司确认的安全缺省。

### B 课题研究 / 战略研发

需求 → 完整性 → 专业评估/成本 → **指定Sponsor** → 产品/研发部门负责人 → 医院/跨区域资源会签（条件） → 重大外部承诺会签（条件） → 适用商务/合规/例外 → PMO立项 → 启动与研发节点 → Sponsor产品阶段决策 → 验收核销。

无Sponsor或战略目标不能提交；PMO不能替Sponsor批准。纯内部研发不强制大区/营销会签或销售订单；只有明确客户收费时记录销售收入。

### C 临床收费 / 过渡生产

需求 → 完整性 → 大区确认真实收费需求 → **产品/市场前置评估** → 研发可实现性 → 分析及成本 → 商务/财务 → 质量/法规/医学 → 授权外例外（条件） → 临时通路/科研立项登记 → 报价合同与启动 → 执行、报告与转产/退出节点 → 验收核销。

产品/市场没通过，研发不能提交。收费项目启动须有报价、合同、支付/授信依据及已审核的合同申请；临时通路须有失效日和转产/退出负责人，交付日不能晚于失效日。到期后阻止继续执行，显示复审/退出事项；不会自动无限续期，也不擅自自动终止客户项目。

## 5. API约定

所有读取须认证及科研成员授权；所有写入另校验角色与状态。匿名401，无科研权限403，字段/流程不满足422，修订号/预算并发冲突409。响应设置private/no-store。

### 查询

- `GET /api/research`：返回当前账号可见items、actor、budgets、customers、policy及integration状态。敏感字段在服务端移除，不依赖前端隐藏。
- `GET /api/research?id=<id>`：当前记录与按权限过滤的操作/版本历史。

### 创建草稿

```json
{"action":"create","clientId":"<UUID，可选且推荐>","route":"A","data":{"title":"项目名称","channel":"月度计划","targetMonth":"2026-10"}}
```

clientId用于Excel行重试去重，同一创建者重复提交返回原记录，不覆盖原值；创建草稿不表示批准。必填资料在提交需求时校验。

### 办理

```json
{"id":"<case_id>","action":"advance","expectedRevision":3,"data":{"当前节点字段":"值"},"note":"批准条件或意见"}
```

action支持save、advance、return、reject、reserve、resubmit、pause、resume、change、submit_milestone、accept_milestone、terminate、archive、submit_document、review_document。只能改当前角色/节点白名单字段，不能传角色或stage来自行跳步。

- 退回/储备：note、data.supplementBy（日期）、data.nextOwner（邮箱）必填。
- 等待/暂停：note、data.waiting（是/否）、data.waitOwner、data.resumeCondition。
- 变更：保留原编号、原基线快照及预算占用，重新评估批准才产生新基线；已审核关联单据与旧节点结果须在新范围下重新确认。
- 节点提交：milestoneId及data.evidence；逾期另有overdueReason、correction。
- 节点验收：指定验收人操作，note必填；B类产品决策必须是Sponsor。
- 关联申请：data.kind为contract/payment/resource/expense/summary，title、evidence、note必填，付款/核销另填amount；审核操作携documentId、decision（approved/returned）及note。

当前变更采用保守的全路由复评，尚未把小额/非关键变更拆成精简影响链，避免未经业务确认就跳过预算、专业或合规重新判断。已发生费用的终止项目必须先核销，不能直接释放全部占用。

### 营销批量预审

```json
{"action":"batch","ids":[{"id":"<id>","revision":8}],"data":{"marketingOpinion":"批准条件","approvalUntil":"2026-12-31"},"note":"本批批准意见"}
```

一次1–30条。每条独立事务、同批次编号，可部分成功；客户端必须展示每条结果，不能把失败条算作已批准。审批时复核预算，竞争同一预算不会超占。

### 预算包维护与CRM主数据

```json
{"action":"budget","id":"BUDGET-001","customerId":"CRM-ID","period":"2026-Q3","total":"100000.00","revision":1,"evidence":"增补批准依据与原因"}
```

仅商务预算角色；既有医院/期间不得替换，不允许直接改已用/锁定。历史已用的首次迁移当前不开放自由录入，需IT提供经过财务确认的迁移程序及对账；避免把不完整预算当作可用余额。

```json
{"action":"customers","records":[{"id":"CRM-ID","name":"医院标准名称","region":"大区"}]}
```

仅全区域商务预算角色，一次1–100条；已有ID不覆盖，回传实际新增数。CRM客户改名、合并及更换区域应走单独主数据治理流程。

## 6. BMP/ERP对接映射与现状

| 中台对象 | BMP建议关联对象 | 当前状态 |
| --- | --- | --- |
| 需求池 / 通道 / 目标月 | 新增科研需求与需求批次 | 规则已实现，实际对象ID待IT |
| 专业评估、成本与路由 | 项目评估及成本明细 | 规则已实现，字段ID待IT |
| 预算包与锁定/核销 | 医院预算台账 / 财务系统 | 中台可运行，主数据Owner与核销时点待定 |
| 主项目编号与七项承诺 | 科研立项申请 → 科研项目管理 | 中台已实现，真实编号映射待定 |
| 中心 / 节点 | 科研明细、里程碑 | 中台已实现，历史多中心去重待导出 |
| 合同 / 付款 / 资源 / 核销 | 报价、合同、付款、物料、ERP、报销对象 | 中台申请可登记审核，外部执行未接通 |
| 交付 / 总结 / 附件 | 成果、文件中心、NAS引用 | 关联受控路径，不复制患者数据，不自动上传 |
| 操作快照 / 待对接事件 | 流程实例、节点审批日志、回调 | 只记录待对接事件，不自动推送 |

现有`lib/integrations/bmp.ts`只提供一个可配置的列表读取适配器，默认路径是待IT确认的占位契约，不是已经验证过的BMP真实API；没有可靠的审批写回接口。原通用`/api/bmp/sync/research`仍服务旧台账，不直接灌入新状态机。

同步建议：

1. IT先提供流程定义、项目主数据、审批日志、多中心映射四包；字段、状态和角色对齐后做历史暂存/对照，不直接赋已批准状态。
2. 确定一套系统为某字段的主写方，建立中台case_id ↔ BMP对象ID ↔ 主项目编号映射；禁止以医院名/项目名作唯一键。
3. 出站事件幂等键为case_id+revision；每个事件带版本、来源、对象ID和业务发生时间。BMP应返回外部ID、处理状态及版本。
4. 断线可重试但不能重复付款/立项；新旧版本冲突进入人工处理，不使用“最后写入覆盖”处理审批。
5. 接口验收前pending_contract事件不发送；批准后再增加worker/调度与重试，不把页面点击成功当作BMP同步成功。

## 7. 身份、数据及部署要求

`RESEARCH_ROLE_BINDINGS`为服务端JSON配置：邮箱映射roles、regions、team。角色：applicant、pmo、technical、analyst、budget、regional、marketing、sponsor、department、product、quality、finance、executive。

```json
{"pmo@example.test":{"roles":["pmo"],"regions":["华南"],"team":"学术支持"}}
```

示例账号无任何真实权限。BMP组织映射尚未提供，默认不授予新登录者业务审批权限；公开页面可演练，但不允许匿名读取正式科研数据。共享团队可见范围、跨区域专业岗是否授予`*`，必须由IT/业务负责人确认。

BMP身份已改为服务端会话校验，旧的可解码身份cookie不能作为审批身份依据；升级迁移后原BMP用户需重新登录一次。令牌只在HttpOnly cookie用于既有BMP连接；数据库存SHA-256哈希及有期限身份，不存密码。自行部署时须使用可信认证网关剥离/重建Sites身份头，不能把公网用户自带同名头视为身份。

部署步骤：

1. 保留现有项目、锁文件和旧迁移；新增迁移`drizzle/0003_nappy_stryfe.sql`。
2. 先在测试D1数据库应用全部迁移；不删除旧research_projects、research_economics和work_items。
3. 配置真实角色、大区、团队和营销授权上限（`RESEARCH_AUTHORIZATION_CENTS`，单位分）；按公司审批确认后填写，不能从前端修改。
4. 导入经确认的CRM医院主数据及可对账预算，配置BMP登录接口并验证服务端会话。
5. 执行自动化测试及下列UAT，再构建、授权发布。

```sh
node --experimental-strip-types --test lib/research/workflow.test.ts lib/research/persistence.test.ts
pnpm run db:migrate:local
pnpm run build
```

数据库测试仅在内存SQLite中运行，不写正式客户记录。正式D1部署的数据库批处理事务及访问策略仍需在公司测试账号下UAT。
