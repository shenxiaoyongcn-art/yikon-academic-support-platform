# 学术支持管理平台与 BMP 系统边界（ADR）

> ADR 编号：ADR-001
> 日期：2026-09-05
> 状态：业务架构基线；BMP 接口与技术事实待 IT 联合确认
> 适用范围：学术支持管理平台、BMP、企业微信微盘／NAS、医检所数据接口之间的建设、交付与验收

## 1. 决策结论

学术支持管理平台定位为**学术支持部的独立业务工作台和智能协同入口**，不是 BMP 的替代系统，也不另建一套公司级客户、联系人、销量、预算或审批主数据。

- **BMP 是公司级业务事实与正式审批的主系统**：统一维护组织与身份、客户／医院、客户联系人、销量、预算包、正式审批记录及 BMP 内既有科研历史数据。
- **本平台是学术支持业务的工作系统**：承载需求评估、科研项目协同、过程管理、会议与专家库、招标、售后、PGT 资质筹建、遗传咨询培训、资料索引、复盘分析和 AI 辅助。
- **企业微信微盘／NAS 是资料正文的受控存储**：在线文档和文件继续保留在原受控位置，本平台保存索引、业务关联、链接、版本与核验记录，不复制形成第二份失控资料。
- **医检所系统是实验室运营指标的事实来源**：扩增成功率、阳性率、阴性率、嵌合率等指标由医检所提供，本平台用于授权范围内的汇总、分析与汇报。
- **跨部门正式动作仍回到 BMP**：凡涉及销售、研发、产品、财务、预算占用、合同、付款、报销、正式立项或公司级审批，均由 BMP 发起或完成；本平台只保存外部对象 ID、只读状态快照和引用核验记录，不在本地作出正式审批。

这一定义允许先把学术支持部需要快速迭代的流程做实，又避免与 BMP 重复建档、重复审批和多口径统计。

## 2. 已知事实与未验证事项

### 2.1 当前可作为设计前提的业务事实

1. BMP 已有科研项目立项与科研项目管理相关流程，但现有流程需要重构和补齐。
2. BMP 已有客户档案、客户联系人、销量、预算包和审批流等公司级能力。
3. 招标、会议、售后、PGT 资质筹建、遗传咨询培训等学术支持业务，不应因为 BMP 暂无完整流程而继续依赖分散表格。
4. 学术支持业务会跨销售、研发、产品、财务等部门，但这些部门的统一办公与审批入口仍是 BMP。

### 2.2 当前不得作出的技术结论

目前没有经过 IT 确认的 BMP 架构说明、源代码、部署拓扑、数据库模型、OpenAPI／Swagger、消息机制或测试环境，因此：

- **不得猜测 BMP 使用何种后端语言、前端框架、数据库或工作流引擎**；
- 不得把项目中的占位接口路径当作 BMP 真实生产 API；
- 不得声称已完成 BMP 双向同步、单点登录或正式审批写回；
- 不得直接连接、读取或写入 BMP 生产数据库。

截至 2026-09-05，对 `https://crm.yikongenomics.com/` 公网登录壳的只读检查只能确认页面标题为 `yikon-bmp`，静态资源具有 Webpack 分块并引用 Element UI 资源；这与常见 Vue 前端构建相符，但**不能据此确定 Vue 版本、后端语言、数据库、工作流引擎或生产接口**。该观察只可用于 UI 兼容评估，不能替代 IT 架构说明。

两套系统是否采用同一种开发语言，不决定能否顺利对接。真正关键的是双方能否共同确认并长期维护：**稳定的对象编号、字段字典、状态语义、接口契约、鉴权方式、幂等规则、回执机制、版本控制和审计链路**。

## 3. 为什么不直接在 BMP 内一次性改完

科研流程和学术支持业务仍在快速调整，直接改 BMP 会把业务试验、公司级正式审批和生产发布绑定在一起，带来四类风险：

1. 需求变化必须等待 BMP 排期，无法快速验证真实使用反馈。
2. 学术支持的专业字段和过程资料进入公司主系统后，容易让界面和流程进一步复杂。
3. 演练状态、部门审核意见与公司正式审批可能被误认为同一法律／财务状态。
4. 未确认 BMP 扩展机制前直接开发，后续接口、权限或升级方式一旦不匹配，返工更大。

因此采用“**BMP 保留公司主数据和正式流程，本平台负责学术支持专业工作，再通过标准接口互联**”的方式。待流程稳定且 IT 评估适合内嵌时，可再决定某些能力是继续独立运行、嵌入 BMP 菜单，还是迁移为 BMP 原生模块。

## 4. 系统职责边界

### 4.1 BMP 负责

- 用户身份、组织、岗位、部门与公司级权限源；
- 客户／医院主档、客户联系人主档及其合并、停用和更正；
- 产品、区域等公司级基础字典；
- 销量、订单等经营事实；
- 预算包、预算余额、占用、释放和财务口径；
- 正式立项、合同、付款、报销及其他公司级审批实例；
- BMP 内已有科研项目及其历史状态；
- 正式审批的转办、加签、驳回、撤回和审计记录。

### 4.2 学术支持管理平台负责

- 学术支持需求受理、预评估、可行性研判与优先级；
- 科研项目的专业评估、人员责任快照、里程碑、风险、月度进展、交付物和成果复盘；
- 会议规划、会前策划、执行核对、会后复盘、效果跟踪、讲题库和专家／讲者库；
- 招标技术材料、售后协同、PGT 资质筹建、遗传咨询培训等学术支持部工作流程；
- 企业微信微盘／NAS 文件的业务索引、版本和引用关系；
- BMP、医检所及部门数据的授权查询、二次分析、看板和汇报；
- AI 检索、分类、摘要、风险提示和初稿生成；
- 所有平台操作日志、同步记录、接口回执和错误待办。

平台可以维护“医院项目负责人、医院对接人、公司项目负责人”等**项目角色快照**，记录其在本项目中的职责、重要程度、确认依据和有效期；人员基本档案仍从 BMP 引用，平台不得另建一套联系人主档。

### 4.3 企业微信微盘／NAS 负责

- 文件正文、在线文档及其原生版本历史；
- 文件级访问权限、共享范围、保留和备份；
- 大文件、视频、PPT、SOP、模板及项目交付资料的受控存放。

平台只保存外部文件 ID、受控链接／路径、业务对象 ID、标题、分类、版本、责任人、更新时间和核验状态。文件迁移、改名、删除、权限变更必须由资料所有者或管理员执行，不由平台静默处理。

### 4.4 医检所系统负责

- 医院、产品、样本／周期等运营事实及指标原始值；
- 指标定义、统计范围、修订记录和质量控制；
- 对外接口中的脱敏、汇总级数据授权。

平台负责展示、趋势分析、异常提示和季度汇报，不改变医检所原始值。涉及患者或样本明细时，必须单独完成最小必要性、脱敏、权限、留痕和合规评审。

## 5. 数据主权矩阵

| 数据对象 | 权威来源／主写系统 | 本平台权限 | 回写原则 | 关键要求 |
| --- | --- | --- | --- | --- |
| 用户、组织、岗位、部门 | BMP／统一身份源 | 只读缓存 | 不回写 | 使用稳定用户 ID，不以姓名或邮箱作唯一键 |
| 客户／医院主档 | BMP | 只读引用 | 更正回 BMP | 保存 BMP 客户 ID、源更新时间、同步时间 |
| 客户联系人主档 | BMP | 只读引用 | 更正回 BMP | 项目内可保存角色快照，不复制联系人主档 |
| 产品、区域等基础字典 | BMP | 只读引用 | 由 BMP 维护 | 字典值须带代码和版本 |
| 销量、订单、经营数据 | BMP | 只读分析 | 不回写 | 保留统计口径、期间、来源和批次 |
| 预算包、余额与正式占用 | BMP | 只读快照与可行性校验 | 不回写；正式动作回 BMP | 平台不得扣减、锁定或释放 BMP 预算，也不得计算或展示第二套“可用余额” |
| 项目成本预测基线 | 本平台 | 主写 | 作为申请材料提交 BMP，不改变 BMP 预算 | 用于项目方案比较、投入产出评估和变更追溯；不是预算占用、财务余额或核销数据 |
| 正式审批实例与结论 | BMP | 只读展示／发起跳转 | 通过正式接口发起 | 无 BMP 实例 ID 和回执不得显示“已审批” |
| 合同、付款、报销等外部单据 | BMP／ERP／公司指定系统 | 只读引用与核验 | 不在平台审批或改写 | 仅保存真实对象 ID、来源状态、版本、核验人和核验时间；“已核验引用”不等于本平台审批通过 |
| BMP 历史科研项目 | BMP | 只读同步 | 更正在 BMP | 与平台新流程分区展示，禁止冒充平台已审批项目 |
| 学术支持新需求与预评估 | 本平台 | 主写 | 需要正式立项时提交 BMP | 平台编号与 BMP 实例编号分别保存 |
| 项目责任人与对接人角色 | BMP 人员主档＋平台项目快照 | 平台主写快照 | 不修改 BMP 人员档案 | 记录职责、重要程度、证据、有效期 |
| 科研协同、里程碑、风险、月报、交付 | 本平台 | 主写 | 必要摘要按契约同步 BMP | 全程留痕和版本控制 |
| 会议计划、执行、复盘 | 本平台 | 主写 | 预算／报销等回 BMP | 与 BMP 客户、产品、销量 ID 关联 |
| 专家／讲者专业档案 | 本平台 | 主写 | 暂不回写；后续按治理决定 | 与 BMP 联系人可建立映射，但不得强行合并 |
| 招标、售后、PGT 筹建、培训工作项 | 本平台 | 主写 | 涉及正式审批时回 BMP | 每项绑定责任人、节点、资料和结果 |
| 文件正文和在线文档 | 微盘／NAS | 只存索引 | 不复制正文 | 外部文件 ID、版本、权限和链接可追溯 |
| 实验室运营指标原始值 | 医检所系统 | 只读分析 | 不回写 | 指标口径、期间、修订版本必须明确 |
| 分析结果、AI 摘要和汇报草稿 | 本平台 | 主写派生结果 | 经人工确认后使用 | 标明来源、生成时间、模型／规则版本和责任人 |

任何来自外部系统的数据，至少保存：`source_system`、`source_object_id`、`source_updated_at`、`synced_at`、`source_version`。对象关联不得使用医院名、项目名或人员姓名作为唯一键。

## 6. 流程边界与状态隔离

### 6.1 科研项目推荐链路

1. 学术支持部在本平台建立需求并完成背景、医院潜力、科研价值、技术可行性、投入产出和风险评估。
2. 平台形成部门意见和所需资料，但此时状态只能是“部门评估中／建议立项／待提交 BMP”等平台状态。
3. 需要公司正式立项、预算或跨部门审批时，由平台生成提交包或通过已验收接口在 BMP 发起流程。
4. BMP 返回正式流程实例 ID、当前节点和处理结果；平台保存回执并展示，不自行推断。
5. BMP 批准后，平台进入项目执行协同，持续维护里程碑、月报、风险、资料和成果。
6. 合同、预算、付款、报销等继续在 BMP／ERP／公司指定系统完成；平台只对真实外部单据的 ID、状态、版本和回执做引用核验，不得设置本地“正式审批通过”。
7. 结题后平台沉淀成果、投入产出、医院价值和可复用资料；需要公司留档的摘要再按契约回传 BMP。

### 6.2 其他模块

会议、招标、售后、PGT 资质筹建、遗传咨询培训可以在本平台形成完整的部门业务闭环；但只要触发公司预算、合同、采购、付款、报销或正式审批，就必须切换到 BMP 正式流程并取得回执。

### 6.3 三组状态必须分开保存

三组状态是三个独立事实，必须使用独立字段、独立更新规则和独立审计记录，不得共用一个 `status` 或相互覆盖。`bmp_status` 只能由匹配 BMP 对象的已验证回执更新；未取得回执时保持“未知／未同步”，不得由平台状态或 HTTP 成功结果推导。

科研流程中，BMP 正式状态组至少要分别保存：正式立项决策及流程实例、预算回执 ID／状态、财务收口回执 ID／状态和源版本。这些字段只允许已验收的入站接口或等效受控交换过程更新，不得出现在正式工作区的可编辑业务表单中。

| 状态组 | 示例 | 权威系统 |
| --- | --- | --- |
| 平台业务状态 `platform_status` | 草稿、评估中、建议立项、执行中、结题、异常 | 本平台 |
| 集成状态 `integration_status` | 未提交、待发送、已发送、已接收、同步失败、待人工处理 | 本平台集成层 |
| BMP 正式状态 `bmp_status` | 待审批、审批中、已通过、已驳回、已撤回、已终止 | BMP 回执 |

界面不得把三组状态压成一个“已完成”。例如：

- “平台评估通过”不等于“BMP 已批准立项”；
- “提交接口成功”不等于“BMP 审批通过”；
- “预算信息已同步”不等于“预算已占用”；
- “项目成本预测已确认”不等于“BMP 预算可用或已占用”；
- “外部合同／付款／报销引用已核验”不等于“本平台已审批”；
- “资料已上传”不等于“正式交付已验收”。

## 7. RACI 责任矩阵

缩写：R＝执行，A＝最终负责，C＝协商，I＝知会。表中的“相关职能”包括销售、研发、产品、财务等实际参与部门。

| 工作项 | 学术支持部 | BMP／流程负责人 | 相关职能 | IT／数据安全 | 微盘／NAS管理员 | 医检所数据方 |
| --- | --- | --- | --- | --- | --- | --- |
| 学术需求收集与专业评估 | A/R | I | C | I | I | C |
| 科研项目部门流程设计 | A/R | C | C | C | I | C |
| 公司正式立项与审批 | C | A/R | R/C | C | I | I |
| 客户、联系人、销量主数据维护 | I | A/R | R/C | C | I | I |
| 项目角色职责和重要程度维护 | A/R | I | C | I | I | I |
| 预算申请、占用、释放和财务结论 | C | A/R | R/C | C | I | I |
| 项目执行、里程碑和风险闭环 | A/R | I | R/C | I | C | C |
| 文件正文、权限和版本管理 | R/C | I | C | C | A/R | I |
| 会议、专家库及学术资产管理 | A/R | I | C | I | C | I |
| 医检所指标定义和原始值 | C | I | I | C | I | A/R |

| 权限、审计和安全事件处置 | C | C | I | A/R | C | C |

每条具体流程还必须在配置或交接表中明确到岗位／人员；RACI 不能替代 BMP 的正式审批人配置。

## 8. 集成契约

### 8.1 建议接口范围

**BMP → 平台（原则上只读）**

- 身份、组织、角色和单点登录结果；
- 客户／医院、联系人、产品和区域字典；
- 销量、订单、预算包及余额；
- 历史科研项目、正式审批实例及状态；
- 单据状态变更回调。

**平台 → BMP（必须逐项审批开放）**

- 发起正式科研立项或其他 BMP 流程的申请包；
- 经人工确认的阶段摘要、结题摘要或资料索引；
- 只传业务必要字段，不直接写 BMP 数据库，也不模拟审批动作。

**医检所 → 平台（只读）**

- 按医院、产品、统计周期汇总的授权指标；
- 指标字典、统计口径、修订版本和数据质量标识。

**微盘／NAS ↔ 平台**

- 优先使用受控文件 ID、元数据、只读预览或跳转链接；
- 上传、改名、移动和权限变更必须使用专用服务身份并单独验收；首期可仅做索引。

### 8.2 统一消息信封

所有增量事件和写入请求建议包含：

```json
{
  "event_id": "全局唯一事件编号",
  "idempotency_key": "业务对象+动作+修订号",
  "source_system": "academic-platform",
  "object_type": "research_case",
  "object_id": "平台稳定对象编号",
  "external_object_id": "BMP对象编号（如已有）",
  "revision": 12,
  "occurred_at": "带时区的业务发生时间",
  "sent_at": "带时区的发送时间",
  "trace_id": "端到端追踪编号",
  "payload": {}
}
```

接收方必须返回接收结果、外部对象 ID、处理状态、当前版本和 `trace_id`。HTTP 200 只代表接口请求成功时，不得被解释为业务审批成功。

### 8.3 幂等、并发与重试

- 同一个 `idempotency_key` 重复到达时只能产生一个业务结果；
- 更新必须携带对象版本，版本冲突返回明确错误并进入人工处理，不做“最后写入覆盖一切”；
- 采用“事件出站箱＋后台发送器＋指数退避＋死信待办”，页面点击不直接等同于跨系统完成；
- 初始全量同步和后续增量同步使用同一映射规则；
- 删除、停用、合并必须传递业务语义，不把源系统缺失记录直接物理删除；
- 所有失败保留请求摘要、响应码、重试次数、最后错误、下一次重试时间和责任人。

### 8.4 对象映射

必须建立独立映射表，至少包含：平台对象 ID、BMP 对象 ID、医检所对象 ID（如适用）、源版本、映射状态、建立方式、核验人、核验时间。名称只能用于人工检索，不能作为系统匹配键。

## 9. 审计与安全要求

1. 优先接入公司统一身份或 BMP SSO；正式环境禁止共享账号。
2. 系统间接口使用最小权限服务身份，密钥进入受控密钥管理，不写入代码、文档、浏览器存储或日志。
3. 全链路使用 TLS；内部接口也须鉴权、限流和来源校验。
4. 操作日志至少记录操作者、角色、对象、动作、前值摘要、后值摘要、时间、来源 IP／设备信息和 `trace_id`。
5. 关键状态、责任人、文件版本和 AI 结论不得无痕覆盖；更正采用新版本或冲销记录。
6. 客户、联系人、销量按区域和岗位授权；导出须受权限控制并记录用途。当前代码以 `PLATFORM_DATA_SCOPES` 作为联调期的服务端区域白名单；未配置区域的普通账号只能读取本人通用工作项，不能读取区域销量或医检所事实。生产环境应改接 BMP／统一身份返回的稳定组织与数据权限，不长期依赖邮箱配置。
7. 患者、样本和遗传数据默认不进入通用平台和通用大模型。确需使用时必须完成专门的数据分级、脱敏、授权、部署和审计评审。
8. AI 仅用于检索、分类、摘要、对比、风险提示和草稿，不替代医学诊断、遗传咨询签署、公司审批或财务决策；每个输出保留来源引用并由责任人确认。
9. 明确日志、同步数据、导出文件和备份的保留期限；到期处置须可审计。
10. 建立备份、恢复演练、安全事件通报和账号离职回收机制。

当前认证适配器只接受显式版本 `yikon-bmp-auth-v1`：请求与响应均须带相同契约版本，响应必须包含 BMP 用户唯一 ID、邮箱、显示姓名、访问令牌和明确有效期，且返回邮箱必须与登录邮箱一致。缺字段、版本不符或仅靠用户自填身份时不得建立会话。该契约是本平台提出的网关适配规范，只有 IT 验收并实现后才可启用，不代表 BMP 当前原生接口已经支持。

销量和医检所指标采用“双门禁”：模块级开关通过后，每一行仍须具备来源系统、外部对象 ID、源版本、源更新时间、同步时间和 `verified` 核验状态，并通过账号区域权限，才允许进入 AI 或管理分析。历史迁移行统一保持 `unverified`，不得自动升级为真实经营事实。

## 10. 分阶段实施

### 阶段 0：事实核验与契约会签

- IT 提供 BMP 架构与接口事实，不依据页面或占位代码猜测；
- 确认主数据、对象 ID、状态字典、权限、接口和测试环境；
- 冻结本 ADR 和科研流程字段的第一版基线。

### 阶段 1：部门工作台可独立使用

- 上线科研需求评估、角色快照、项目协同、进展、风险、文件索引和汇报；
- 客户、联系人、预算和销量暂以经确认的只读导入或测试接口接入；
- 可跳转 BMP 办理正式审批；人工登记的 BMP／ERP 单据编号只能作为“待核验引用”，不能使正式状态或财务节点完成；
- 依赖正式立项、预算变更或财务收口的节点，在已验收回执尚未接入时必须阻断，不得用自由文本绕过。

### 阶段 2：BMP 只读互联

- 接入 SSO、客户／联系人、产品／区域、销量、预算、历史科研和审批状态；
- 建立增量同步、对象映射、失败待办和审计看板；
- 完成与真实数据口径的对账。

### 阶段 3：正式流程联动

- 平台可按契约发起 BMP 正式流程；
- BMP 回调审批节点和结果，平台保持三组状态隔离；
- 通过幂等、并发、重试、撤回、驳回和异常恢复联合验收后才能启用生产写入。

### 阶段 4：分析与 AI 增强

- 接入医检所指标及更完整的经营数据；
- 上线产品／医院／学术支持人员维度分析、科研投入产出、会议效果和季度汇报；
- AI 先在脱敏数据和可追溯知识库中使用，经过准确率、权限、引用和人工确认验收后逐步扩大范围。

## 11. IT 必须确认的清单

### BMP 技术与部署事实

- BMP 产品版本、部署方式、前后端技术栈、数据库和工作流引擎；
- 是否提供 API 网关、OpenAPI／Swagger、SDK、Webhook、消息队列或数据库只读视图；
- 可用的开发／测试／预生产环境及脱敏样例数据；
- 生产发布、变更、回滚和故障责任流程。

### 身份与权限

- SSO 协议、令牌生命周期、用户／组织／岗位稳定 ID；
- 区域、医院、产品和跨部门数据权限规则；
- 服务账号申请、密钥托管、IP 白名单和证书要求；
- 离职、转岗、代理、转办、加签等行为由谁处理。

### 对象与口径

- 客户、医院、联系人、产品、区域、销量、预算、科研项目和审批实例的唯一 ID；
- 字段字典、必填项、枚举、金额与日期精度、时区和历史修订规则；
- 客户／联系人合并、停用、删除和编号变更的通知机制；
- 销量口径、退货／冲销、预算余额／占用／释放的业务语义；
- BMP 现有科研流程的节点、角色、问题字段和可扩展范围。

### 接口与运行保障

- 全量与增量读取方式、分页、限流、最大批次、超时和 SLA；
- 正式流程发起、附件引用、撤回、驳回和状态查询接口；
- 回调签名、重放保护、幂等键、版本冲突和错误码；
- 日志查询、追踪编号、监控告警、补数、重试和人工修复机制；
- 数据保留、备份恢复、等保／内控和安全审计要求。

以上各项未确认前，只能使用模拟数据、脱敏样例或只读导入，不开放生产写入。

## 12. UAT 联合验收场景

| 编号 | 场景 | 必须通过的结果 |
| --- | --- | --- |
| UAT-01 | SSO、转岗和离职 | 用户身份、组织和权限与权威源一致；离职后立即失去访问权限 |
| UAT-02 | 查询客户与联系人 | 平台只能读取和引用；修改入口指向 BMP，不产生第二份主档 |
| UAT-03 | 客户／联系人合并 | BMP 合并后平台映射正确迁移，历史项目仍可追溯，不按姓名误配 |
| UAT-04 | 销量与预算对账 | 抽样记录的对象、期间、金额／数量、版本和来源与 BMP 一致；平台仅显示 BMP 只读预算快照，项目成本预测基线单独展示且不扣减 BMP 余额、不产生第二套可用余额 |
| UAT-05 | 新科研需求评估 | 平台可完整记录背景、负责人／对接人职责、重要程度、成本估算、证据和部门意见 |
| UAT-06 | 发起 BMP 正式立项 | 同一修订重复提交只生成一个 BMP 实例；平台取得实例 ID 和回执 |
| UAT-07 | 状态隔离 | 平台评估、集成传输、BMP 审批三组状态分别保存和显示；正式立项、预算和收口回执字段不在业务表单中开放手工编辑，无已验证回执时不得显示“已审批／已占用／已收口” |
| UAT-08 | 驳回、撤回和再次提交 | 原审批历史保留，新修订重新提交，编号、版本和处理人均可追溯 |
| UAT-09 | 并发更新 | 两人同时修改时出现明确冲突提示，不静默覆盖 |
| UAT-10 | 接口中断与重放 | 请求进入重试／人工待办；恢复后不重复建项目、不丢事件，`trace_id` 可贯通查询 |
| UAT-11 | 文件索引与权限 | 平台链接打开受控原文件；版本、权限变化可识别，无权用户不能绕过微盘／NAS 授权 |
| UAT-12 | 医检所指标 | 指标值、口径、医院、产品、期间和版本可追溯；修订后历史版本仍可核验 |
| UAT-13 | AI 输出 | 输出带来源和生成信息；缺少证据时明确提示；未经人工确认不触发审批或改写事实 |
| UAT-14 | 审计与导出 | 关键操作和导出均有操作者、时间、对象、用途和追踪号；越权访问被拒绝并告警 |
| UAT-15 | 备份与恢复 | 在约定恢复目标内恢复测试数据，版本、对象映射和审计记录完整 |
| UAT-16 | 外部单据引用 | 合同、付款、报销只能通过真实外部对象 ID 和回执核验；平台无本地正式审批按钮或状态，项目收口不会自动把费用核销标为完成 |

每个场景必须使用双方确认的脱敏样例和预期结果。同步时延、可用性、恢复时间、数据保留期限等数值指标由 IT 与业务共同会签，不在缺少生产条件时擅自承诺。

## 13. 上线门禁

满足以下条件后，才可从“部门试运行”进入“生产联动”：

1. 本 ADR、字段字典、状态字典、RACI 和接口契约完成业务与 IT 会签；
2. BMP 主数据和正式流程的主权未被平台重复实现；
3. 全部生产写接口通过 UAT、权限、安全、幂等、异常恢复和审计验收；
4. 微盘／NAS 权限和文件索引规则完成资料管理员确认；
5. 医检所数据范围和合规要求完成数据方确认；
6. 上线、监控、故障、回滚、补数和责任人安排清楚；
7. 业务使用手册明确区分平台状态与 BMP 正式状态。

本 ADR 是后续科研模块、会议模块及其他学术支持模块设计的上位边界。任何新功能若要改变数据主写方或替代 BMP 正式审批，必须先新增 ADR 并重新会签，不能在页面开发中隐性改变。
