# 学术会议与 KOL／讲者库落地实施计划

> 版本：2026-09-05
> 用途：交付 IT 进行数据建模、接口开发、真实数据迁移和 UAT 验收
> 适用模块：推广会议、会议日历、科室会、KOL／优秀讲者库、讲题库、会议资料库、会议效果复盘

## 1. 先明确当前事实

当前会议模块仍是“通用工作台账 + 静态演示内容”，只能用于说明页面结构和初步交互，**不能视为可正式使用的会议管理系统**。

- 页面中的固定场次、客户数、商机数、转化金额和示例会议属于静态展示，不是真实经营结论。
- 当前通用 Excel 导入只读取首张工作表并按通用字段写入，不能正确处理会议规划表、月份日历页、区域 KOL 页、多值医院／产品／姓名、日期区间及历史版本。
- 当前界面虽有 BMP 同步、云盘路径等入口，但在没有经过 IT 验收的 BMP API、身份鉴权、对象编号、回执和微盘／NAS 接口前，**不得声称 BMP、企业微信微盘或 NAS 已经接通**。
- 未取得 BMP 流程实例 ID、预算单号或审批回执的记录，只能显示为“平台草稿／部门协同记录”，不得显示为“BMP 已审批”。
- 本计划定义的是待实现的生产方案，不代表下述数据已经导入，也不代表接口已经上线。

## 2. 首批真实数据基线

### 2.1 唯一首批导入来源

| 数据域 | 源文件 | 首批唯一数据页 | 核查基线 | 明确排除 |
| --- | --- | --- | --- | --- |
| 会议规划 | `⭐️学术支持部-2026年会议规划表（区域自办线下会、全国自办会、全国赞助会）.xlsx` | `总表` | 35 条核心可导入记录 | 月份页只作为原表展示，不重复导入 |
| KOL／讲者 | `产品KOL+优秀讲者库-v1-20260904.xlsx` | `总表` | 204 位去重后的有效专家／讲者 | 区域页不重复导入 |

首批迁移必须以两个文件的 `总表` 为唯一业务数据来源。月份页、区域页可能与总表重复、滞后或存在不同展示方式，只保留为核对证据，不得作为第二批记录再次写入。

### 2.2 已发现的数据问题

下列问题不得在后台静默修正，必须进入“导入预览—待确认”队列：

- 表头不一定在第一行，需识别并显示最终采用的表头行号；无法唯一识别时禁止提交。
- 会议规划中约 12 条日期为自由文本、日期区间或含糊表达，不能直接推算为精确日期。
- 会议规划中约 16 条存在复合医院、复合题目或一格多对象，需要人工拆分或明确保留为一个联合会议。
- KOL 总表中约 33 条缺少单位／医院，不能仅凭姓名自动匹配 BMP 客户或联系人。
- KOL 总表中有 2 条“一格多人”，必须拆成人员记录后再确认。
- KOL 表中有 3 条疑似 2016 年的日期异常，应保留原值并标记核验，不得擅自改成 2026 年。
- 同一人姓名相同但单位、科室或职称不同，不得直接合并；同一医院存在简称、曾用名时，必须通过 BMP 医院 ID 或人工映射确认。

原文件不得覆盖。每次导入都要保留文件哈希、工作表、源行号、原始单元格值和确认人，使任何正式记录都能追溯回源文件。

## 3. 数据与系统边界

### 3.1 数据归口

| 数据对象 | 权威来源／主写系统 | 本平台处理方式 |
| --- | --- | --- |
| 客户／医院、客户联系人 | BMP | 只读调用；本平台不得另建第二套客户联系人档案 |
| 销量、订单、产品经营数据 | BMP | 只读分析；保留期间、口径、BMP 对象 ID 和同步时间 |
| 预算包、合同、付款、报销、正式审批 | BMP | 只读展示或跳转；本平台只保存单号、状态和回执 |
| 学术会议计划、策划、执行、跟进、复盘 | 本平台 | 主写并全过程留痕 |
| KOL／讲者专业档案、讲题、会议历史 | 本平台 | 主写；可映射 BMP 联系人 ID，但不得反向覆盖 BMP 档案 |
| PPT、方案、海报、录屏、会议纪要等正文 | 企业微信微盘／NAS | 正文留在原受控存储，本平台只存文件索引、版本、权限状态和业务关系 |
| 会议效果派生指标、AI 摘要 | 本平台 | 标明数据来源、截止时间、计算规则和人工确认状态 |

KOL 和 BMP 客户联系人是两个不同业务对象：前者记录学术影响力、产品认知、演讲能力、历史场次和培养路径；后者是公司客户主档。两者可以建立一对一或多对一映射，但不能强制合并，也不能以姓名作为唯一键。

### 3.2 接口真实性规则

1. BMP、微盘或 NAS 接口没有配置或调用失败时，页面必须明确显示“未配置／连接失败／待人工处理”，不得返回模拟成功。
2. 本地演示数据必须标注 `demo`，不得与 `manual`、`excel_import`、`bmp_sync` 等正式来源混合统计。
3. 外部数据至少保存 `source_system`、`source_object_id`、`source_updated_at`、`synced_at` 和 `source_version`。
4. 对 BMP 采用只读优先策略；任何写回、发起审批或预算动作必须另行完成接口、安全和回执验收。
5. 不直接连接或写入 BMP 生产数据库；通过 IT 批准的 API、消息或中间交换层对接。

## 4. 专用数据模型

不能继续用一个通用 `work_items` 表承载会议和 KOL。建议采用下列专用表；字段命名可按现有技术规范调整，但业务对象和关系不得压缩丢失。

### 4.1 导入与审计

#### `import_batches`

- `id`：平台批次 UUID
- `domain`：`events`／`experts`
- `file_name`、`file_sha256`、`file_size`
- `selected_sheet_name`、`header_row_number`
- `source_version`、`uploaded_by`、`uploaded_at`
- `status`：`uploaded`／`previewed`／`needs_review`／`committed`／`failed`
- `total_rows`、`valid_rows`、`warning_rows`、`blocked_rows`、`committed_rows`
- `committed_by`、`committed_at`

#### `import_rows`

- `id`、`batch_id`、`sheet_name`、`source_row_number`
- `raw_cells_json`：按原表保存原始单元格值
- `normalized_json`：规范化后的候选值
- `row_fingerprint`：规范化关键字段哈希
- `validation_status`：`valid`／`warning`／`blocked`
- `issue_codes_json`、`review_comment`
- `resolution`：`create`／`update`／`merge`／`skip`
- `target_object_id`、`confirmed_by`、`confirmed_at`

文件哈希用于识别整份文件重复上传；行指纹用于识别跨版本重复记录。两者都不能取代人工确认异常行。

### 4.2 会议主数据

#### `academic_events`

- 平台会议 UUID、会议业务编号、名称
- 会议类型、会议层级、举办形式，三个字段分别保存
- 计划日期原文、标准开始／结束时间、时区、日期确认状态
- 主办方、承办方、区域、城市、场地／线上平台
- 学术目标、业务目标、客户画像、预期观念变化、预期转化
- 当前阶段、业务状态、负责人、协作人、下一动作和截止时间
- BMP 预算／审批／报销等外部单据编号与状态，只读展示
- 来源、创建批次、源行号、版本、创建／更新时间、归档标记

#### 会议关系表

- `event_hospitals`：会议与 BMP 医院 ID，多对多；记录医院在本场会议中的目标、角色及优先级。
- `event_products`：会议与 BMP 产品 ID／标准产品代码，多对多；组合产品必须拆分保存。
- `event_people`：主席、主持、讲者、讨论嘉宾、内部负责人、销售对接人、备选专家及确认状态。
- `event_topics`：讲题方向、最终题目、版本、内容审核状态和讲题库引用。
- `event_checklists`：会前、会中、会后检查项、责任人、截止时间和完成证据。
- `event_followups`：D+7／D+30／D+90 节点、对象、动作、结果、下一步、证据和逾期状态。
- `event_files`：微盘／NAS 文件 ID、链接、分类、版本、权限状态、核验时间和会议关系。
- `event_external_refs`：BMP 流程、预算、合同、付款、报销等单号、状态和最后同步时间。
- `event_effect_samples`：会议—医院—产品粒度的会前三个月、会后 M1–M3、首单、复购、份额、观念与项目节点。

### 4.3 KOL／讲者与讲题库

#### `experts`

- 专家 UUID、姓名、姓名规范化值
- 当前单位、科室、职称、行政职务、城市／区域
- BMP 医院 ID、可选 BMP 联系人 ID、映射状态和确认人
- 学术影响力、友好度／合作度、产品认知、演讲能力
- KOL 层级：区域 KOL／中央 KOL／培养中；星级和评估依据分开保存
- 擅长产品、疾病／技术方向、可讲题目、会议角色偏好
- 负责人、最近联系时间、可用性、合规／授权状态
- 来源批次、源行号、数据完整度、状态、创建／更新时间

多单位、多科室、多产品、多讲题、多地区都必须使用关系表，不得用逗号拼接后作为唯一检索字段。

#### 相关表

- `expert_affiliations`：专家单位／科室任职历史和有效期。
- `expert_product_tags`：专家与标准产品标签及认知／合作程度。
- `expert_topic_tags`：专家与专业方向、疾病或技术标签。
- `expert_event_history`：专家参与会议、角色、讲题、反馈、材料和履约情况。
- `topic_library`：标准讲题、适用产品、适用客户阶段、目标、讲者、最新版资料索引和内容审核状态。
- `topic_asset_versions`：PPT／案例／主持稿等外部文件版本及使用历史。

专家劳务标准应引用公司统一规则或 BMP 单据，不在专家主档中固化“永久价格”。个人联系方式、证件和支付信息如确需使用，必须单独进行权限、加密和保留期设计；首期不建议导入。

## 5. 导入流程：必须先预览，再提交

### 5.1 标准流程

1. **上传**：计算 SHA-256；若同域同哈希已有已提交批次，直接提示重复，不再写入。
2. **选源**：默认只允许选择 `总表`；用户若选择月份页／区域页，界面需提示其仅供核对并禁止首批提交。
3. **识别表头**：扫描候选表头行，显示识别结果、字段映射和置信度；人工确认后继续。
4. **解析原值**：完整保存 `raw_cells_json`、文件哈希、工作表和源行号。
5. **规范化**：处理空格、全半角、标准日期、医院／产品别名，但不覆盖原值。
6. **校验与匹配**：关联 BMP 医院／产品 ID，检查复合对象、缺单位、一格多人、日期含糊和潜在重复。
7. **预览**：分别展示可直接提交、警告待确认、阻断三类；支持逐条拆分、映射、合并、跳过。
8. **提交**：只有确认人点击提交后才写入正式表；一个数据库事务内完成目标记录、来源关系和审计日志。
9. **结果报告**：返回新增、更新、合并、跳过、失败和待处理数量，并可下载问题清单。
10. **重放验证**：同一文件再次提交必须做到零重复；修正后的新版本只更新被确认的对象。

### 5.2 幂等与去重

- 会议优先使用未来建立的稳定会议业务编号；历史数据没有编号时，使用“标准日期／日期原文 + 规范化会议名称 + 标准产品 + 目标医院”生成候选指纹。
- KOL 优先使用平台 UUID + 已确认的 BMP 医院／联系人映射；历史首次导入以“规范化姓名 + 单位 + 科室”生成候选指纹。
- 指纹相同只代表“可能重复”，跨文件更新仍需显示字段差异和来源，禁止静默覆盖。
- 任何合并都必须保存被合并对象、字段取值依据、操作人和时间，并支持审计回查。

## 6. API 契约建议

以下为本平台内部专用 API 设计目标，最终路径可按项目规范调整。未开发或未配置时应返回明确的 `501/503`，不能用演示数据返回 `200`。

### 6.1 导入 API

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| `POST` | `/api/imports/events/preview` | 上传会议 Excel，返回批次、表头识别、字段映射、逐行问题和候选匹配 |
| `POST` | `/api/imports/experts/preview` | 上传 KOL Excel，返回同上 |
| `PATCH` | `/api/imports/{batchId}/rows/{rowId}` | 保存拆分、映射、合并、跳过等人工处理结果 |
| `POST` | `/api/imports/{batchId}/commit` | 对已确认行执行幂等提交 |
| `GET` | `/api/imports/{batchId}` | 查询批次、问题和提交结果 |
| `GET` | `/api/imports/{batchId}/issues.xlsx` | 导出待处理清单 |

`preview` 不得写入正式业务表；`commit` 必须校验批次版本，防止多人同时修改后提交旧结果。

### 6.2 业务 API

| 资源 | 最少能力 |
| --- | --- |
| `/api/events` | 列表、条件查询、新建草稿、修改、归档、导出 |
| `/api/events/calendar` | 按月／周返回标准时间、状态、类型和负责人，不保存第二份日历数据 |
| `/api/events/{id}/people` | 维护会议角色、讲者、备选专家和确认状态 |
| `/api/events/{id}/checklists` | 维护会前／会中／会后任务和完成证据 |
| `/api/events/{id}/followups` | 维护 D+7／30／90 结果和下一动作 |
| `/api/events/{id}/effects` | 读取 BMP 销量并维护观念、首单、复购、项目节点等效果数据 |
| `/api/experts` | KOL 检索、建档、更新、归档、导出和重复候选提示 |
| `/api/experts/{id}/history` | 返回参与场次、角色、讲题、反馈和资料索引 |
| `/api/topics` | 讲题库检索、版本、适用场景、讲者和资料索引 |

所有列表 API 都要支持分页、权限过滤、更新时间增量查询；所有写入 API 都要记录操作者、变更前后值和请求追踪编号。

## 7. 产品功能设计

### 7.1 会议类型、层级和形式必须拆分

三个概念不能混在一个下拉框：

- **会议类型**：科室会、MDT、院内学术会、城市沙龙、区域自办会、全国自办会、药企合办会、第三方学术赞助、遗传咨询培训班、线上专题会、其他。
- **会议层级**：科室／医院、城市、区域／省级、全国、国际。
- **举办形式**：线下、线上、线上线下结合。

另外单独维护主办／赞助属性、目标客户画像、产品方向和会议目的。赞助会还需维护已争取权益：讲题、讲者、品牌露出、展位、病例或客户触达等，避免“只记录花了多少钱”。

### 7.2 会议日历

- 日历直接读取 `academic_events`，不再人工维护一套月份页。
- 支持月／周／列表视图，按负责人、区域、类型、产品、医院、状态筛选。
- 日期未确认的会议进入“待排期”栏，不强行落到某一天。
- 延期保留原计划日期和变更原因；拟召开、已召开、取消不能混合统计。
- 点击日历事项进入同一会议详情，不能生成重复记录。

### 7.3 科室会快捷申请

科室会是高频场景，提供“1 分钟建草稿”的快捷入口，首屏只要求：

1. BMP 医院及科室；
2. 计划日期或待定月份；
3. 关联产品；
4. 本次目标和客户画像；
5. 负责人；
6. 线下／线上／混合形式。

讲者、预算引用、议程、物料和资料可在草稿保存后补充。需要正式预算或审批时跳转／提交 BMP，并显示 BMP 实例 ID 和状态；平台不得自行显示“已批准”。

### 7.4 KOL／讲者库和讲题库

- 支持按姓名、单位、科室、区域、产品、专业方向、KOL 层级、演讲能力和历史会议检索。
- 角色要区分主持人、主席、讲者、讨论嘉宾和备选专家，不能只存“参会专家”。
- 每次会议结束后回写本平台专家履历：角色、讲题、现场表现、产品认同、履约情况、材料版本、后续培养动作。
- KOL 评价至少包含学术影响力、友好度／合作度、产品认知和演讲能力；星级必须有评估依据和更新时间。
- 区域 KOL 与中央 KOL 分层维护，并记录培养目标和复评时间。
- 讲题库按技术方向、临床应用、案例分享等场景分类，保存适用产品、客户阶段、最新版课件索引和审核状态，减少重复做 PPT。
- 讲者临时变动风险必须维护同职级备选专家及确认状态。

## 8. 会前—会中—会后闭环

### 8.1 会前策划

- 明确底层目标：观念传递、客户开发、上量、业务赋能、KOL 培养或科研机会。
- 记录目标医院的 BMP 基础信息和销量基线，但不在平台重复维护客户档案。
- 完成客户画像、目标产品、销量缺口、决策人／开单主力、角色分配和备选专家。
- 维护学术框架、讲题方向、PPT 收集与内容审核、预埋问题和讨论环节。
- 引用 BMP 预算包和审批状态；校验劳务标准，同一学会／同类角色标准不一致时提醒。
- 使用风险清单：时间／讲者是否锁定、预算是否超出、物料是否到位、线上测试、交通住宿、权限与合规。

### 8.2 会中执行

- 会前 30–60 分钟完成音视频、PPT、直播、会场和角色到位检查。
- 记录实际到场／在线人员、关键客户、临时变更、异常和处理结果。
- 主持、讲者、讨论嘉宾的实际履约与议题完成情况分别记录。
- 录屏、照片和客户信息采集必须遵守授权；平台只保存资料索引和权限状态。

### 8.3 会后闭环

- D+1–3：回访高价值客户和未到场客户，记录观念变化、下一步病例／项目／上量动作。
- D+7：完成会议复盘、问题清单、资料归档、专家反馈和负责人下一动作。
- D+30：核对首单、复购、病例入口、客户观念、科研机会、销量变化和未转化原因。
- D+90：完成三个月阶段效果判断、可复制打法、未转化责任动作和后续培养计划。
- 所有跟进都必须明确对象、动作、结果、下一步、责任人、日期和证据，不能只勾选“已完成”。

## 9. 三个月效果复盘口径

会议效果按“会议—医院—产品”粒度计算，销售结果以 BMP 为准，观念、首单、病例入口和项目节点由业务人员补充证据。

1. 保留原会议日期，同时增加标准日期；日期区间保留原文并以确认后的首日确定跟踪月份。
2. 会前三个月均值为基线；会后 M1、M2、M3 从会议次月连续计算，会议当月不得作为 M1。
3. 基线三个月或 M1–M3 任一缺失，只显示“阶段观察”，不得提前给最终有效性结论；空白表示未知，不补零。
4. 增长率为 `会后三个月均值 ÷ 会前三个月均值 - 1`。
5. 基线为 0 且会后有销量，标记“从 0 突破”；前后均为 0，标记“无增量”。
6. 完整医院—产品样本增长超过 10%，或实现从 0 突破，判定该样本有效；一场会议的完整样本中有效占比超过 50%，方可判定该会议有效。
7. 负数销量先核实退货、冲销或口径调整，未确认前不得纳入核心有效率。
8. 会议和增长只能表述为关联或推动，不能无依据认定为唯一因果。
9. 所有百分比同时展示分子、分母、统计单位、截止日期、数据来源和完整样本数。

系统需同时展示“客户观念、病例／患者入口、首单／复购、销量／份额、科研／项目节点”等不同结果，不能只用一个“有效／无效”替代业务事实。

## 10. 资料存储与归档

会议资料正文继续放在企业微信微盘或 NAS，平台建立可搜索索引，至少包含：

- 外部文件 ID、受控链接／路径、文件名、资料分类和 MIME 类型；
- 关联会议、专家、讲题、医院、产品和流程节点；
- 版本号、上传人、更新时间、文件哈希和“当前有效版本”标记；
- 权限状态、最后核验时间、失效链接提示；
- 资料类型：立项／审批引用、会议方案、议程、讲者 PPT、海报／邀请函、主持稿、签到、照片／录屏、费用单据引用、复盘报告、后续跟进。

平台搜索资料时应返回“标题 + 业务关系 + 版本 + 跳转链接”，不复制正文形成第二套版本。微盘／NAS 未提供 API 时，首期允许人工粘贴受控链接并由系统定期提示核验，但页面必须标注“人工索引”，不能显示“云盘已同步”。

## 11. 分阶段实施

### P0：先做到真实、可用、可追溯

1. 删除或明确隔离会议静态演示指标，正式统计只读取真实记录。
2. 建立会议、KOL、讲题、导入批次、源行和审计专用表。
3. 完成两个 `总表` 的 `preview → 人工确认 → commit` 导入链路。
4. 录入首批 35 条会议规划和 204 位去重 KOL；异常行不强行提交，保留待处理清单。
5. 上线会议列表、会议日历、待排期、科室会快捷申请、KOL 检索和讲题检索。
6. 上线会前／会中／会后检查、D+7／30／90 待办、资料索引和 Excel 导出。
7. BMP 医院／联系人／销量／预算未接通时采用“待配置”状态；允许保存 BMP 外部编号，但不模拟同步成功。

P0 完成后，团队应能用真实数据新建和跟踪会议，不再依赖演示记录；但正式审批、预算、合同、付款和报销仍在 BMP 完成。

### P1：打通只读数据和效果闭环

1. 对接 BMP 单点登录或统一身份、医院、联系人、产品字典、销量、预算包和正式流程状态的只读接口。
2. 完成医院／产品／联系人映射工作台及同步错误待办。
3. 按会议—医院—产品生成会前三个月和会后 M1–M3 数据，并实现完整性校验。
4. 建立 KOL 历史场次、表现、讲题版本和培养计划。
5. 完成赞助权益、劳务规则引用、线上／线下执行清单和异常复盘。
6. 建立会议规划、执行质量、D+7／30／90、产品和医院维度看板。

### P2：自动化与智能分析

1. 在权限允许时接入微盘／NAS 元数据 API，自动校验链接、版本和权限，不复制正文。
2. AI 辅助生成会议方案、主持稿、复盘初稿、KOL 推荐理由和未转化原因摘要；输出必须有来源和人工确认。
3. 基于真实会前／会后数据生成季度 PPT 草稿和产品攻坚建议。
4. 只有 BMP 提供正式且验收通过的写入接口后，才评估从平台发起 BMP 流程；仍以 BMP 回执为最终状态。

## 12. UAT 验收标准

### 12.1 数据迁移

- [ ] 会议只从会议规划 `总表` 形成 35 条首批候选，月份页没有产生重复记录。
- [ ] KOL 只从 KOL `总表` 形成 204 位去重有效候选，区域页没有产生重复记录。
- [ ] 系统展示并保存表头行号、文件 SHA-256、工作表、源行号和原始单元格值。
- [ ] 模糊日期、复合医院／姓名、缺单位和疑似异常年份全部进入预览待确认，未被静默修正。
- [ ] 同一文件重复提交不新增记录；新版本能显示字段差异和合并依据。
- [ ] 导入结果可导出新增、更新、合并、跳过、失败和待处理明细。

### 12.2 日常操作

- [ ] 科室会可在 1 分钟内保存最小草稿，后续补充讲者、预算引用、材料和议程。
- [ ] 会议类型、层级、形式分别筛选和统计。
- [ ] 日历与会议列表读取同一份数据；延期保留原日期和原因，日期待定记录进入待排期。
- [ ] KOL 可按单位、科室、区域、产品、层级、演讲能力和历史场次检索。
- [ ] 一个专家可关联多单位／产品／讲题；历史场次可追到会议、角色、讲题和资料版本。
- [ ] 会前、会中、会后任务均有责任人、截止时间和证据；逾期可查询。
- [ ] D+7／30／90 自动生成待办，完成记录包含事实结果和下一动作。

### 12.3 系统边界与可信度

- [ ] 平台不能修改 BMP 客户、联系人、销量和预算主数据。
- [ ] 正式审批、预算、合同、付款和报销仅显示 BMP 单号与回执；没有回执时不显示“已审批／已付款”。
- [ ] BMP 或微盘／NAS 未配置、超时、无权限时明确报错，不返回模拟成功。
- [ ] 演示记录与正式记录隔离，不进入经营统计和导出。
- [ ] 文件正文仍在微盘／NAS；平台索引可追溯版本，失效链接有提示。
- [ ] 权限至少区分查看、编辑、提交导入、确认合并、管理 KOL、查看销量和管理员；全部写操作有审计日志。

### 12.4 效果复盘

- [ ] M1 从会议次月开始，系统能阻止把会议当月当作 M1。
- [ ] 数据不足三个月时仅显示“阶段观察”，空白不补零。
- [ ] 增长率、从 0 突破、完整样本和会议有效率按第 9 节规则复算一致。
- [ ] 每个比例均显示分子、分母、截止日期和来源；负数销量未核实前不进入核心有效率。
- [ ] 按医院、产品、区域、负责人和会议类型导出的明细能追溯到 BMP 数据批次及平台跟进证据。

## 13. IT 开工前必须确认的输入

1. BMP 的正式 API／OpenAPI 文档、测试环境、鉴权方式、医院／联系人／产品／销量／预算／审批对象 ID 和状态字典。
2. 单点登录或用户组织同步方式，以及学术支持部、销售、财务、产品、研发的权限范围。
3. 企业微信微盘／NAS 是否提供文件元数据、受控预览、链接校验和服务账号；若无 API，确认首期人工索引规则。
4. 两个 Excel 总表的字段负责人，以及所有异常行的业务确认人。
5. 医院、产品、区域、会议类型、KOL 层级、讲题方向和资料分类的标准字典及维护责任人。
6. 销量统计口径、月结时间、退货／冲销处理规则和会议效果截止日。
7. 日志保留期、敏感信息范围、导出权限、备份恢复和生产发布流程。

以上输入未确认前，可以完成 P0 的平台业务能力和真实 Excel 数据预览，但不得在生产页面标注“BMP 已接通”“云盘已同步”或“正式审批已完成”。

## 14. 最终交付物

- 数据库迁移脚本、数据字典和实体关系说明；
- 两套 Excel 专用导入映射、异常规则、预览／提交接口和迁移报告；
- 会议列表、日历、科室会快捷申请、KOL／讲题库、流程检查、跟进和资料索引；
- BMP／微盘／NAS 接口契约、配置说明、错误处理和回执示例；
- 权限矩阵、审计说明、备份恢复方案和安全检查结果；
- 自动化测试、UAT 用例与结果、性能基线、上线／回滚方案；
- 真实数据口径说明：导入数、待处理数、完整样本数、统计截止日期和数据来源。

本计划的上线原则只有一句：**先把真实数据、业务责任、来源和状态做准确，再做自动化和 AI；没有真实接口与回执，就如实显示未接通。**
